Git workflow - набор правил и практик, определяющих, как команда использует Git для ветвления, слияния и доставки кода. Существуют несколько основных моделей, выбор которых зависит от частоты релизов и размера команды.

## Виды моделей:

- **Github Flow** - легковесная модель для команд, которые развёртывают код регулярно. Основная ветка **main** всегда готова к развёртыванию. Для новых функций создаются коротки ветки, после рецензии они сливаются обратно в **main**. Модель подходит для непрерывной доставки и небольших команд, не требуя сложных структур веток.
- **Gitflow** - строгая модель с параллельными ветками **main**(для релизов) и **develop**(для интеграции). Ветви функции создаются из **develop**, а для подготовки к выпуску используются ветви **release** и **hotfix**. Она лучше всего подходит для проектов с запланированными релизами, но может быть избыточной для команд с высокой скоростью разработки.
- **Trunk-Based Development** - подход, при котором вся работа ведется в одной главной ветке, а незавершённые функции скрываются с помощью флагов. Ветви живут не дольше одного дня, что требует высокой зрелости **CI/CD** и автоматизированного тестирования, но максимизирует скорость и минимизирует конфликты слияния.
- **Feature Branch Workflow** — базовая модель, где каждая новая функция разрабатывается в отдельной ветке, которая затем сливается с основной веткой (часто `develop`). Это простой способ изолировать изменения и подходит для команд, переходящих от **SVN** или начинающих работать с **Git**.
- **GitLab Flow** — это упрощенная стратегия ветвления в Git, которая объединяет разработку на основе функций с отслеживанием задач и CI/CD, предлагая легкую альтернативу сложному GitFlow. В отличие от классических моделей, она использует **одну основную ветку** (`main` или `master`) для интеграции кода и **ветки окружений** (например, `staging`, `production`) для контроля развертывания.
